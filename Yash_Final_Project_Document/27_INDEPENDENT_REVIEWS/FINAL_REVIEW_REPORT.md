### 1.3 Method limits stated plainly

- One reviewer applied seven lenses (product, architecture, security, data integrity, failure modes, cost and complexity, requirements consistency). This is not seven independent reviews.
- After the initial review, two actual read-only specialist passes checked contracts/state/consent and security/offline/operations. They spot-checked rather than re-audited all 46 findings. The post-review table identifies which conclusions they support and what remains unverified.
- The 22 final review questions: the brief's text was not available to the reviewer. Only the first ("Are any important domains missing?") and last ("Is any architectural complexity unnecessary?") were quoted. Questions 2 to 21 in §4 are the council's reconstruction from the review lenses it was told to apply. Whoever owns the brief should map them.
- Severity scale: **Critical** = as written, an implementation would breach a stated safety, privacy or integrity invariant, or two invariants cannot both hold. **High** = cross-document contradiction or gap in a core contract that causes rework or a defect if built as written. **Medium** = inconsistency, unsupported claim or missing definition with a bounded blast radius. **Low** = clarity, hygiene or labelling.

### 1.4 What held up under checking

- Evidence of care in honesty labelling: [TARGET]/[OPEN]/[REF] tags, `V(src)` versus `U` in PLT-01 with no `V(dev)` claimed, "no number is a measurement" in OPS-SLO, "documentation status is not implementation status" in README, PROJECT_SCOPE and PROJECT_MASTER.
- COMPLIANCE_APPLICABILITY_MATRIX hedges every row ("applicability to be confirmed by counsel"); SOC 2 is labelled an aspiration; WCAG 2.2 AA is "a design target, no conformance measured" (ACCESSIBILITY_SPEC).
- The ADR register records the strongest counter-argument per decision; ADR-T03's mitigation (typed module contract, `MF_MODE`) is a good hedge. The problem is that later documents undo the hedge (REVW-07).
- Arithmetic in the two scoring tables is correct; most headline counts reproduce; internal links resolve; the example registry validates against its own schema.
- Backend core pattern is coherent across BE-01, DB-02 and the intent of SM-BGJOB: transactional outbox, `FOR UPDATE SKIP LOCKED`, fenced leases, consumer inbox dedupe.

## Appendix B. Method notes for reproducing the mechanical checks

All checks were small Python scripts run against the Markdown, YAML and JSON in this folder: link resolution (relative links only, anchors ignored); regex extraction of table rows by first-cell ID; PyYAML parse of `openapi.yaml` and `asyncapi.yaml`; `jsonschema` (draft 2020-12) validation of `REMOTE_REGISTRY.example.json` against the two schemas with a `referencing` registry; recomputation of the two weighted tables; intersection of AC, BR, INV and FF identifiers between `05_*`, `06_*`, `16_*` and `22_*`. Limits: identifier matching is textual, so an AC cited in prose without its ID would be missed; the test catalog uses no ID ranges, so that gap is unlikely to affect REVW-17. Counts of "features without an AC" use the FEAT number embedded in AC IDs and therefore treat an AC filed under a different FEAT number as not covering a feature.
