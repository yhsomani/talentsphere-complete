## A. Executive assessment

TalentSphere connects career identity, evidence, learning, applications and recruiter decisions. Its strongest implemented foundation is the Fastify API with server-side authorization, a PostgreSQL-backed core write path, and explicit separation of verified evidence from claims. This audit assumes a small beta with one API writer per database; no traffic forecast or team capacity was supplied.

**Release verdict: not ready for a public beta or GA on the evidence available.** The default memory-mode suite passed **1,172 tests in 115 files**, the migration-history helper passed **5 tests**, and non-emitting checks passed for all ten TypeScript projects. Formatting failed in seven pre-existing files. No current PostgreSQL, browser, live-email, deployment, restore, or accessibility-conformance result was obtained. These gaps are release evidence gaps, not proof that those systems fail.

Two focused probes reproduced defects: arbitrary non-executable challenge text receives `passed`/`100`, and six leased background jobs execute nine times with two synthetic workers. Evidence from challenges remains explicitly unverified; the new UI also says submissions are unscored. Those protections should stay. Correct the API result and worker lease behavior before expanding user-facing features.

The previous assessment of 16 implemented / 78 partial / 75 absent is preserved below as history. Under the stricter requested vocabulary, the provisional portfolio is **6 implemented-unverified, 87 partial, 1 broken, 75 not implemented (search-limited), 4 deprecated/not recommended**. Zero whole features are newly certified implemented-and-verified. These are triage classifications, not 173 completed acceptance reviews.

Recommend a restricted, owner-approved beta around identity, profile, evidence verification, job discovery/application, recruiter review, messaging and account controls. The PRD's GA loop also requires learning, assessment/practice, portfolio, outcomes and career progression. A narrower beta must not silently redefine GA. Keep payment, predictive hiring, proctoring and other gated capabilities behind their existing decisions. The [delivery plan](FEATURE_PLAN_2026-10-21.md) separates release urgency from the unchanged registry scores.

**Audit completeness:** all 173 features, 248 business rules, 28 journeys, 274 direct route registrations, 51 migration files and 684 tracked files are inventoried. High-risk paths received targeted inspection; all remaining semantic, subfeature and end-to-end coverage gaps are explicit in the [machine-readable evidence ledger](AUDIT_EVIDENCE_2026-10-21.json). Exhaustive feature acceptance and production verification remain incomplete. No revenue, conversion, cost, usage or capacity metrics were supplied; this is not a business-performance measurement.

## E. Architecture and reliability assessment

Current topology is React/Vite → Fastify → shared contracts/domain → PostgreSQL and in-process read model, plus a separate PostgreSQL job worker. `persist()` commits core operations before updating Maps, guards concurrent writes in process, and delegates transaction/conditional update enforcement to `PgCoreStore`. The retained advisory-lock connection refuses a second API writer; lost lease fails traffic closed. This is a deliberate constraint, not permission for additional replicas. Hydration reads the core dataset at boot; volume-dependent startup and memory limits remain unmeasured.

Static route count: **274 registrations, 70 durable-registry entries, 3 stateless, 201 ephemeral-header routes**. These are route labels, not 70 independently proven durable workflows. For example, erasure execution persists core data but is not in the durable set; certificate proof can combine durable evidence with ephemeral certificates. Inspect the storage path as well as the header. The ledger retains all route methods, paths and source lines.

SQL inventory is 51 files, including 00043 alignment, private-data/security follow-ups, 00050 admin audit and 00051 flags. The clean-migration/idempotency/PG gates already exist in CI. Migration file presence and passing ledger helper tests do not establish application against a target, correct backfills, hosted-role grants or production RLS. Keep direct client domain writes disabled and preserve server-authoritative access checks.

The AI career assistant is a local heuristic, not an external model integration. Two assistant routes call `assertAIAssistanceAllowed`; this does not prove every future AI entry point or restart case is covered. Sessions/usage/conversations are process-local. No paid inference was invoked; provider authorization and entitlements remain separate. Browser sessions remain bearer tokens in localStorage; any cookie migration needs the #49 CSRF/CORS/session design, not an incidental audit edit.

No architectural rewrite or route-module split is justified merely by the server's size. Keep focused fixes at shared ownership boundaries. Profile measured boot/hot paths before changing persistence/read-model architecture. No code or dependency deletions are proposed without a separate impact analysis.

### D-09: verified course credentials omit the required assessment gate

**P0 before exposing LMS certificates as assessed capability.** SSOT F-07 core
behavior 8 and canonical BR-048 require a passing final assessment (at least 70%).
`apps/api/src/server.ts` checks only completed lesson count before marking the
enrollment complete, creating `authority_verified` evidence and minting a verified
certificate (completion block around lines 5254-5289). It does not read a final
assessment attempt or score there. This is separate from D-01 challenge simulation.

The existing `tests/integration/lms-courses.test.ts` progression test completes
three lessons without an assessment, then asserts a verified certificate, 50 XP,
a public valid result and an authority-verified propagation job. Rerun with native
config loading and no cache: all six tests passed. That confirms current memory-mode
behavior, not BR-048 compliance. Built workspace dependency provenance and absence
of PostgreSQL/browser verification still limit the result.

The same block mutates lesson progress and enrollment completion before awaiting
durable evidence persistence. Static recovery risk: if that persistence fails, a
retry hits the already-completed lesson branch and does not retry issuance. This
failure mode has not been injected and remains an explicit acceptance test.

Keep F-07/F-52 partial. X-11 must enforce the canonical assessment gate, retain
idempotency and provide recoverable issuance. Changing what counts as assessed or
authority-verified evidence requires the owner review already required for trust
policy; do not silently redefine a certificate as proof of capability.

### D-10: certificate and evidence revocation are independent

**P0 before presenting linked credentials as a consistent trust signal; static
finding, not a new runtime reproduction.** Course issuance creates both an evidence
record and a certificate containing its `evidenceId`. Certificate revocation
(`apps/api/src/server.ts:5449`) replaces three certificate Map entries and appends
an in-memory audit event; it does not revoke the linked evidence. Evidence
revocation (`server.ts:1559`) persists evidence but does not update a linked
certificate. The unified verifier independently reads either record, according to
which hash was supplied. The worker's evidence event handler records the event;
it does not reconcile these records.

Consequently the inspected paths permit inconsistent validity between linked proof
representations. Existing `certificate-verification.test.ts` checks the certificate
hash after revocation, not the linked evidence hash. No cross-proof assertion or
PostgreSQL restart result is claimed. SSOT section 6.3 requires revoked evidence to
affect dependent signals; BR-149 requires append-only revocation history. The test's
BR-154 label is also misleading: canonical BR-154 describes the dispute appeal SLA,
not revocation authorization.

Extend X-11 to define the authoritative revocation relationship, preserve history,
and check both proof URLs before/after revocation and restart. Preserve legitimate
independent evidence; do not cascade blindly or change trust policy without owner
review. F-52/F-96 remain partial pending that contract and verification.

## Cross-cutting risks

- **Most backend modules are not durable.** `apps/api/src/durability.ts` lists the routes backed by Postgres. Everything else is held in process memory and returns `x-talentsphere-durability: ephemeral`. Every Partial feature with an API loses its data on restart.
- **Most Partial features have no UI.** Skills graph, career, salaries, reputation, talent pools, interviews, referrals, endorsements, warm intros, admin, moderation, certificates and learning impact are all API-only. A user cannot reach them from the web app.
- **Billing is simulated and not wired.** Checkout shows plans and does not call `/billing/subscribe`. The README already says paid plans cannot be bought.
- **No outbound email.** The worker's mail provider is for development. Verification codes reach users only through the dev outbox.

## What to add next

Ordered by value for the effort. Items 1–3 use code that already exists.

1. **Durable storage for the long-tail modules.** Move the in-memory modules behind `persist()` and add their tables (ADR-015 is the pattern). Do this before adding more features, so new data is not lost on restart.
2. **Web screens for existing APIs, highest value first:**
   - Referrals (F-142) and warm intros (F-121): the network page can host them.
   - Endorsements (F-110) and peer credibility (F-150): add endorse buttons to profile and work history.
   - Public certificate verification (F-52): add a `/verify/:hash` route, which the API already serves.
   - Admin console (F-17, F-35, F-83) and moderation queue (F-24): needed to operate the platform.
   - Saved searches and job alerts (F-32): the job page already runs searches.
   - Skills graph (F-84) and career transitions (F-85, F-95): a profile tab each.
3. **Wire billing for real.** Connect the checkout to `/billing/subscribe` in simulated mode, clearly labelled, and gate the candidate plan (F-61). This turns a static page into a working flow.
4. **Digest job (F-29).** Add a worker job that sends the digest once an email provider exists. The preference is already stored.
5. **Quiz and course reviews (F-68, F-72).** `LessonContentType` already includes `quiz`, and the instructor review pattern can be reused for course ratings.
6. **Service worker (PWA claim).** Add offline caching for the app shell, or stop describing the app as offline-capable.
7. **Interview room UI (F-33, F-88).** The join, consent and scorecard APIs exist, so a candidate and interviewer screen is mostly UI work.
8. **New features not in the registry yet:** a member directory so Network search finds people without typing a name, and an email-verified outreach flow for recruiters. Both reuse existing APIs.
