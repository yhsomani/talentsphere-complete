# End-to-end audit — 2026-10-21

Browser-driven audit of the web app and its API with `playwright-cli`, plus direct API probes. Every number below comes from a run in this session. Anything not run is listed under "Coverage gaps".

## Method and environment

- **Isolated stack.** The API on :4000 was already running and is stale (it returns 404 for `GET /api/v1/auth/session`, which exists in `apps/api/src/server.ts`). It was not used. The audit ran against the current source: API on :4100 (`STORAGE=memory`, pinned test token secret, rate limits raised) and the web dev server on :5199 proxying to it. Both were stopped afterwards. No dev-database data was touched.
- **Accounts.** Candidate A, candidate B, a recruiter, and a platform administrator (promoted with an ops token, the same way the e2e suite does it).
- **Browser.** Chromium only, desktop 1280×900 and mobile 390×844.
- **Reticle overlay.** The dev server injects Reticle's tour and settings panel. It showed up as extra dialogs and unlabeled buttons in a few checks. Those were tooling artifacts and are counted as such below.

### Environment finding

The API on :4000 does not register `GET /api/v1/auth/session`, so every signed-in page there that depends on the session fails. It needs a restart from the current build. The two persistence changes made earlier in this session (admin audit log, feature flags) are also not live there.

## Security and data-integrity findings

Held up under test:

- Admin routes return 401 unauthenticated and 403 for candidates and recruiters; candidates cannot grant themselves roles, toggle flags or maintenance.
- A token with its roles edited, garbage tokens, `alg:none` and non-Bearer schemes are all rejected; faking `platform_admin` in `localStorage` reveals no admin data.
- Registration cannot grant admin (`role` or extra `roles[]`); profile mass-assignment cannot change roles or owner.
- IDOR: candidate B cannot read, transition or list candidate A's application, applicants of someone else's job, or a thread B is not part of.
- Wrong password and unknown user return the same message; login honors `?return=` only for in-app paths (three external forms tested).
- XSS payloads in name, headline, job title and description, search, work-history company, and messages render as text. Double-click on sign-in, apply, add project, add role, send message and suspend each produce one request.
- Admin governance: self-suspend and self-demotion are refused, a reason is required, suspension takes effect on the next request, audit entries carry the reason, and reactivation works. A suspended user can still sign in by design (the handler documents it) but the session is confined and the UI says the account is restricted.
- Sign-out-other-devices ends the other session and keeps the current one.

## Coverage gaps (not tested)

- Rate limiting and lockout: raised in the audit stack, so brute-force limits were not exercised.
- Postgres mode end to end: the stack ran in memory mode; durability was covered only by the pg tests already in the repo.
- Real email (verification codes, digests), payments (checkout only renders), file upload and resume export, certificate verification, reference-giving with a real token, interview and the other API-only features.
- Other browsers (Firefox, WebKit) and real devices; screen-reader behavior beyond labels, headings, focus trap and focus visibility.
- A second recruiter's organization (cross-organization IDOR on hiring) and large datasets or pagination.
- Session expiry by TTL (revocation and garbage tokens were tested instead).
- The skip link was not verified as the first Tab stop on a signed-in page (H04 inconclusive); it exists and moves focus to main content.
- Reticle verdict for F-17: not produced. F-17 was verified with Playwright against the isolated stack.

## Release readiness

Not ready for a public release as it stands:

1. The stored-XSS link issue is fixed here but the fix is uncommitted and the shared dev API is stale.
2. Weak passwords are accepted and maintenance mode is inert; both need a decision.
3. Only the memory-backed path and Chromium were browser-tested; the Postgres path and other browsers were not.

The core career loop (sign up, profile, work history, apply, review, notifications, messaging, networking) behaved correctly under normal and abnormal input, and authorization held in every case tried.
