## Legacy Documentation Disposition Plan

_Former file: `PRODUCT_BLUEPRINT/11_LEGACY_DISPOSITION/DISPOSITION_PLAN.md`._

How the pre-existing documentation relates to this blueprint, what is kept, what is superseded, and the gated procedure for deleting what is no longer needed.

### 1. Position in this change

The owner asked that old documents be used where required and **deleted once their need is complete**. This change does **not** delete anything, for four reasons that can each be checked:

1. **Ratification is not done.** `DEC-001` records that the blueprint does not supersede `docs/SSOT.md` until `OD-PRD-31` defines ratification. Deleting the document the blueprint has not yet replaced would leave the project without an accepted source.
2. **Automated checks read legacy files.** `tests/unit/pricing-consistency.test.ts` reads `docs/PRICING.md`; `tests/security/route-authz-sweep.test.ts` reads `docs/system-model/06-route-authorization.md`. Deleting those files fails the test suite.
3. **Repository rules point at them.** `CLAUDE.md`, `AGENTS.md`, `README.md`, `ARCHITECTURE.md`, source comments in `packages/contracts`, `packages/domain` and `packages/ui`, SQL migration comments, `.prettierignore` and the CI workflow header reference `SSOT.md` or `docs/`.
4. **Some legacy files are the only record of what is built.** The blueprint describes the intended product; `ARCHITECTURE.md` and `docs/reports/` record the as-built state and dated evidence. They are not superseded by it.

So deletion is specified as a gated procedure (section 5), not performed here. Everything stays recoverable from git history either way.

### 5. Gated deletion procedure

Run only after the owner closes `OD-PRD-30` and `OD-PRD-31`. Each step is a precondition for the next.

1. **Ratify** the blueprint baseline (`OD-PRD-31`) and record a `DEC-` entry naming which legacy classes may be deleted.
2. **Verify coverage:** [`LEGACY_FEATURE_COVERAGE.md`](#legacy-feature-coverage-f-01-to-f-173) has no row without a disposition; the [integrity report](09_REGISTERS/OTHER_REGISTERS.md#integrity_reportmd) has no unexplained dangling reference to legacy ids; the owner has reviewed every `[DEC-REQ]` conflict that cites a legacy value.
3. **Move as-built facts** that exist only in a doomed file into `ARCHITECTURE.md` or `docs/reports/` (for example ADR-015 and ADR-016).
4. **Fix references.** Update `README.md`, `docs/INDEX.md` and documentation comments. Comments in source, migrations, `ci.yml` and `.prettierignore` are in or near protected build files: needs explicit owner approval per `AGENTS.md`; until then keep stub files at the old paths that point to the blueprint.
5. **Run the checks** that read documentation (`pnpm test`) and the link check; they must pass before and after.
6. **Delete in one reviewed change** limited to the classes named in step 1; keep the mapping files in this folder so legacy ids stay explainable.
7. **Tag** the last commit containing the legacy set so it can be restored from history.

### 6. What is not proposed

No change is proposed to application code, configuration, migrations, dependencies or infrastructure. The blueprint references them only as inputs.

## Legacy Feature Coverage (F-01 to F-173)

_Former file: `PRODUCT_BLUEPRINT/11_LEGACY_DISPOSITION/LEGACY_FEATURE_COVERAGE.md`._

> Status: intended-product traceability. Nothing here is a claim that anything is built. This file proves that the blueprint in `PRODUCT_BLUEPRINT/` accounts for every feature of the legacy registry `docs/registries/FEATURE_REGISTRY.md` (F-01 to F-173; detail in `SSOT.md` §7 and §9 and `docs/archive/target-blueprint/05_FEATURE_SPECIFICATIONS.md`). Legacy status columns are ignored on purpose; see `../00_START_HERE/CONVENTIONS.md` §1.

### 1. Method

1. Every legacy feature was checked against the `Source` lines and headings of all feature specifications in `../02_MODULES/` and against the module trace sections (module section 15).
2. A feature is marked Covered when one or more `FR-` ids specify it directly. It is marked Merged when its scope is absorbed into broader features and the legacy name has no separate feature. It is marked Deprecated-dropped when the registry itself marks it DEPRECATED or NOT RECOMMENDED. It is marked Gap-closed when no feature covered it, so a new `FR-` was added in this pass.
3. Legacy descriptions were taken from the registry title, `SSOT.md` §7 and §9, and the plain-language intent column of `docs/reports/FEATURE_STATUS_2026-10-21.md` (used for meaning only, never for status).
4. Before a gap was closed, existing features were searched for the same concept under another name. Where one was found, the legacy id was added to that feature's `Source` line instead of creating a duplicate.
5. Every `FR-` id in the table was checked to exist as a `###` heading in a module file, and every range was expanded and checked id by id.
